# Annotate — operating instructions

Turn a markdown document into a browser-based review surface. The reviewer selects text, leaves Suggested edits / Comments / Deletions, and exports a structured `.annotations.md` file that an AI reads to apply changes.

The output is a single self-contained `.html` file: open it in any browser, no server and no build step. Annotations persist in `localStorage` and export to markdown on demand.

## When to invoke

Triggered by:
- "/annotate <path>"
- "let me annotate this"
- "make this reviewable"
- "I want to mark up this doc"
- "create an annotation page for X"

Also reasonable to suggest proactively when:
- The AI has produced a long proposal, plan, or draft document and the user says they need to "read through it"
- Multiple paragraphs need targeted feedback rather than whole-section decisions
- A draft will go through a few back-and-forth cycles

Do NOT use for:
- HTML files (v1 supports markdown only)

## How to generate a review file

This skill has no separate build script. The generator is the short command below: it reads the bundled `template-annotate.html` (which sits next to this SKILL.md in the skill directory), injects the source markdown, and writes `<basename>.review.html` next to the source.

**Steps:**
1. Resolve the absolute path of `template-annotate.html` in this skill's own directory. It is a sibling of this SKILL.md. If you are unsure where the skill lives, locate it (e.g. `find ~ -path '*/skills/annotate/template-annotate.html' 2>/dev/null | head -1`).
2. Run, substituting `<SOURCE.md>` (the document to review) and `<TEMPLATE>` (the path from step 1):

```bash
python3 - "<SOURCE.md>" "<TEMPLATE>" <<'PY'
import sys, hashlib, json, pathlib
src = pathlib.Path(sys.argv[1]).resolve()
tpl = pathlib.Path(sys.argv[2]).read_text(encoding="utf-8")
md  = src.read_text(encoding="utf-8")
sha = hashlib.sha256(md.encode("utf-8")).hexdigest()
out = (tpl.replace("{{SOURCE_FILENAME_JSON}}", json.dumps(src.name))
          .replace("{{SOURCE_SHA_JSON}}", json.dumps(sha))
          .replace("{{SOURCE_FILENAME}}", src.name)
          .replace("{{SOURCE_SHA}}", sha)
          .replace("{{SOURCE_MARKDOWN}}", md.replace("</script>", "<\\/script>")))
dst = src.with_suffix(".review.html")
dst.write_text(out, encoding="utf-8")
print("Wrote:", dst)
PY
```

The command handles SHA-256 computation, the five placeholder substitutions, and `</script>` escaping. The five `{{...}}` placeholders it fills are defined in `template-annotate.html`; do not rename them on either side. The only runtime dependency is Python 3 (standard library only).

Then report back the output path, how to open it (`open <path>` on macOS, `xdg-open <path>` on Linux, `start <path>` on Windows), and a one-line reminder of how the loop works. Example: "Annotate in the browser, click Copy for Claude, paste the markdown back here."

## Naming conventions

| File | Purpose |
|------|---------|
| `<basename>.md` | The source document |
| `<basename>.review.html` | The browser review file (generated by this skill) |
| `<basename>.annotations.md` | The export the reviewer hands back to the AI |

Always co-locate all three in the same directory.

## Applying annotations the reviewer returns

When the reviewer pastes back the contents of `<basename>.annotations.md`, or hands you the file:

1. **Read the original source** (`<basename>.md`) and the annotations file.
2. **For each `SUGGEST` entry**: locate the `Selected` text in the source near the indicated `L<line>`. Apply the `Replace with` change as a string replacement.
3. **For each `DELETE` entry**: locate the `Selected` text in the source near the indicated `L<line>`. Remove it (replace with empty string). Clean up adjacent whitespace or orphaned punctuation if removal would leave a dangling fragment. If a `Why` is present, treat it as context, not as a request for confirmation.
4. **For each `COMMENT` entry**: do not modify the source. Include the note in your response — answer any implicit questions, address the point, or ask for direction. Legacy `QUESTION` entries in older exports should be treated the same as `COMMENT`.
5. **For the `Notes for Claude` preamble**: this is high-level direction. Apply it to your overall approach (e.g. "keep changes minimal" or "confirm with the team before finalizing"). Surface anything that constrains the rest of the work.
6. **If a `SUGGEST` or `DELETE` anchor can't be found verbatim in the source**: stop and flag it explicitly. Show the annotation, the line number, and ask whether the source has moved or whether to apply by fuzzy match. Never silently guess.
7. **Verify the SHA**: the annotations file lists the source SHA at the top. If the current source SHA differs, warn the reviewer — their annotations are anchored to a version that no longer matches.

## The export format the reviewer will hand back

```markdown
# Annotations: product-spec.md
Source SHA: a3f2b1c4d5e6...
Reviewed: 2026-05-19 14:32
Annotations: 3

## Notes for Claude

Keep changes scoped to the onboarding section. Don't touch the API examples.

## Annotations

### SUGGEST · L142
Selected: users must verify their email before continuing
Replace with: users must verify their email before accessing billing
Why: too broad — only billing needs verification

### COMMENT · L267-L269
Selected: the trial lasts 14 days
Note: confirm with product. Is it 14 or 30 now?

### DELETE · L455
Selected: and any associated legacy migration steps
Why: removed in v3, no longer relevant
```

Order: annotations are sorted by line number (ascending), then by character offset within a line. Process them in source-file order to keep edits clean.

## Visual system

The template uses an Edward Tufte–inspired layout (see https://edwardtufte.github.io/tufte-css/): off-white paper (`#fffff8`), dark ink, a book serif (Newsreader) with **italic headlines** (h2/h3 weight 400, no rules), links that inherit the ink color and underline rather than recolor. Optimized for readability, scannability, and ease on the eyes.

**Layout.** The text sits in a left-weighted column (~36rem measure) with an open right margin where annotations render as **sidenotes** floated next to the text they reference, each tied to a small superscript number in the prose. Source line numbers are not shown in the UI; they are kept on each block (`data-line-start`) only for anchoring and the export (`L<n>`).

**Margin-only.** Annotations live as sidenotes in the right margin, with no separate list or drawer. Below ~1024px the right margin can't hold them, so they reflow inline beneath the text they reference.

Three accent colors map to annotation types (used for the underline, the superscript, and the sidenote's left rule):

| Type | Color | Use |
|------|-------|-----|
| `SUGGEST` | blue (`--suggest: #2F5E8F`) | "change this to that" |
| `COMMENT` | yellow-gold (`--comment: #B0840A`) | inline note, no edit needed. Phrase questions in the note body. |
| `DELETE` | brick red (`--delete: #A6403B`) | "remove this entirely" — line-through style preview |

Do not invent additional annotation types. If a user asks for one, push back unless the loop genuinely breaks without it.

Legacy: prior versions had a `QUESTION` type. Stored `question` annotations are auto-migrated to `comment` on load. Old `.annotations.md` files may still contain `### QUESTION` entries; treat them as comments when applying.

## What this skill deliberately does not do

- **No HTML source input.** Only markdown. HTML would require a different anchor strategy.
- **No threading / replies.** One author, one round per file.
- **No auto-save to disk.** localStorage holds state; export is explicit. (Browsers can't write to the file system without a local server.)
- **No multi-document review.** One file per review session.
- **No automatic AI round-trip.** The reviewer copies or downloads, then pastes back. The loop is explicit on purpose.

If a request bumps into one of these boundaries, surface the tradeoff before adding scope.

## Anchoring model

Annotations anchor to a single **leaf block** (a `<p>`, `<li>`, `<h2>` — never a container like a `<ul>`) plus the selected text within it. Reliability rules baked into the template:

- **Selections anchor to the block where they START.** A selection that spans multiple blocks (e.g. two bullets) is **clamped to the start block** — the highlight covers the portion in that block, the note still applies. This is deliberate: cross-block selections used to silently fail to render.
- **Render re-locates by text, not just line.** On load, each annotation is matched to the leaf block whose text actually contains its selected text (nearest to the stored line). Resilient to line drift and container/leaf mismatches.
- **Never silently lost.** If an annotation can't be placed in the document (e.g. the source text changed), it still renders as a flagged sidenote (`⚠ not found in document`) at the end of the doc, rather than vanishing. Re-make it against the current text.
- **Toolbar press never loses the selection.** The selection toolbar `preventDefault`s its mousedown so clicking a type button can't collapse the selection mid-create.

## Known fragility

- **localStorage is the only persistence.** Browser data clear / different profile / private window = annotations lost. The top bar shows "saved Xs ago" prominently and the Export button is the primary CTA. This is the deliberately-accepted risk.
- **The custom markdown renderer is minimal.** It handles headings, paragraphs, lists, blockquotes, code blocks, simple pipe tables, and inline bold/italic/code/links. Exotic markdown (footnotes, definition lists, MDX) will render as plain text. For prose and proposal docs this is fine; flag it if the source uses unusual syntax.
- **Editing the source after generating** changes its SHA: the page's mismatch banner fires, and annotations keyed to the old SHA won't surface. Regenerate the review file and re-annotate.
